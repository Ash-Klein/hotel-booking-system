## 2. 每张图的设计要点

### 图3-1 用例图

- 6 类角色：顾客、门店前台、门店店长、集团财务、集团运营管理员、城市经理（只读）。
- 15 个顶层用例，按模块配色；细节（锁房 15/30 分钟、范围外功能）放在图例/注释，避免图过大。
- 店长用**参与者泛化**（`前台 <|-- 店长`）表达"权限上位"：前台能做的入住/退房/异常/查询，店长自动继承；店长只额外画库存、价格、锁房、退款审批、报表。
- No-show 由夜审在 24:00 自动判定（REQ-019），**不作为人工用例**；异常经"处理异常订单"承接。
- **布局按端分区**：左侧门店端（顾客 / 前台 / 店长），右侧集团端（财务 / 管理员 / 城市经理）。右侧角色用反向关联 `用例 <-- 角色` 写，只为让 PlantUML 把人排到右边，语义仍是角色发起用例。
- 刻意不画会员积分、OTA 对接、电子发票、房态管理——这些在实验一已被否决（REQ-038/050）。

### 图3-2 类图

- 11 个核心类，覆盖库存、订单、支付、履约四个域。
- 关键约束写在 note 里：
  - `DailyInventory` 唯一键 `(hotelId, roomTypeId, bizDate)`，`available = total - sold - locked ≥ 0`；
  - `OrderItem` 保存房型/价格快照，历史订单不受基础资料变更影响；
  - 订单状态取值与禁止转换；
  - 退款 > 500 元需店长审批。
- 支撑实体（Staff/Role/StaffHotel/OperationLog/OrderChange/Cancellation/ReconciliationBill）未展开，留给报告数据字典；如果答辩要求权限设计，建议再补一张小类图。

### 图3-3 组件图

- 三层：接入层（4 端 + API 网关）→ 应用服务（M1–M7）→ 基础设施（MySQL 主从、Redis、支付网关）。
- 关键依赖：M3/M5 → M2（库存）、M3 ↔ M4（支付单/回调）、M6 → 只读从库。
- 为了让自动布局可读，去掉了包框，层次靠底部图例说明；这是有意取舍。

### 图3-4 状态图

- 7 个状态 + 初始/终止；守卫条件与动作写在转换标签上。
- 三类取消来源合并为一条"取消 / 释放库存"边，细节在 note；如果要逐条展开，人工修改时可拆成三条。
- 明确列出禁止转换（已入住不可取消、已入住/离店不可改单）。

### 图3-5 活动图

- 纵向主流程，动作前缀标明责任方（顾客/预订服务/库存服务/支付网关/门店前台/通知服务）。
- 没有用泳道：PlantUML 在泳道内嵌套分支时连线会乱穿（已实测），改用"责任前缀 + 注释"保证可读。
- 覆盖：幂等校验、逐日库存校验、条件更新、线上/到店两种支付、超时释放、失败提示保留已填信息。

### 图3-6 时序图

- 用 `autonumber` 编号，`alt` 画 15 分钟超时释放。
- 核心信息：A 的条件更新影响行数=1，B 的=0；只有一单成功。
- 数据库条件更新是最终判定，Redis 只做缓存/加速（注释里说明，未画 Redis 生命线，避免误导）。

### 图3-7 部署图

- 用户侧 → Nginx → 应用集群（≥2 节点）→ MySQL 主从 / Redis 哨兵 / 对象存储 / 支付网关。
- 标注 RPO≈0、可用性 99.9%，以及门店断网"手工登记、恢复补录"的降级路径。

## 2.1 协议锁房在各图中的落点（2026-11-10 补充）

协议锁房（REQ-008）不是一个订单状态，而是"把 N 间房从公开可售中预留出来"的库存动作。它必须同时出现在库存口径、架构和流程说明里，否则图与图之间会打架。

| 图 | 落点 | 说明 |
|---|---|---|
| 用例图 | 店长 → 协议锁房 | 创建/释放是店长的用例 |
| 类图 | `GroupLock` + `DailyInventory.groupLocked` | `available = total - sold - locked - groupLocked`；`GroupLock` 增加 `releaseAt` |
| 时序图 | `WHERE total - sold - locked - group_locked >= 1` | 抢最后一间时先扣协议占用；图中假设 `group_locked = 0` |
| 组件图 | M2 的 note + 图例 S3 | 锁房写 `group_lock`、逐日累加；到期由 S3 调度释放 |
| 状态图 | 底部图例 | 明确"协议锁房不进入订单状态机"，单独管理生效/释放/转订单 |
| 活动图 | 底部图例 | 协议锁房由店长单独创建，不经过散客下单流程 |
| 部署图 | "调度任务"节点 | 负责订单超时、协议锁房到期，以及夜审 No-show 判定 |

尚未落到图上的：协议锁房在 UI（库存日历）中的展示，等 UI 阶段补。

## 3. 已知问题（人工修改时优先处理）

1. **用例图偏长（1470×2023）**：15 个用例纵向排列，A4 整页可读但偏小。建议拆成"顾客与门店端""集团端"两张，或压缩到 10 个顶层用例。
2. **类图偏宽（4142×1711）**：建议横排整页；若要竖排，需再拆"交易域/支撑域"。
3. **部署图有两条跨线**（报表只读、导出文件），可调整节点声明顺序或改用 `left to right direction` 重排。
4. **组件图没有包框**：层次靠图例，若老师要求严格分层，可手工加 `package` 后微调。
5. **活动图无泳道**：责任方写在动作前缀；若必须用泳道，建议只保留"顾客 / 系统 / 门店"三条，避免嵌套切换。
6. **支撑实体未进类图**：权限、审计、改单/取消记录只在 note 与数据字典里，答辩可能被问。
