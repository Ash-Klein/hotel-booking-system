# 摘 要

本报告以实验一《酒店预订系统需求规格说明》的 51 条需求为输入，完成 7 个业务模块 + 3 项支撑能力的架构设计、7 张 UML 图与 14 屏 UI，并记录 8 次 AI 辅助设计及人工修改。报告重点说明两个决策：订单采用“一单一房型、一个日期区间”；门店异常按“前台发起、集团审核、财务/运营协助核实”三分权。

**关键词**：酒店预订系统；UML；面向对象设计；UI 设计；AI 辅助

# 第一章 实验目的

本次实验在实验一需求基线之上完成一次可落地、可追溯的设计，具体目标如下。

- 掌握面向对象的设计方法：从需求中识别实体、职责、边界与交互，用封装、分离与快照控制复杂度。
- 熟练使用 UML 描述设计思路：能按表达目的选择图种，并保证图与图、图与需求之间不矛盾。
- 掌握 UI 设计工具：完成信息架构、栅格、状态与交互设计，让每一屏都能追溯到模块与需求。
- 建立可审查的过程：用 Git 记录 AI 初稿与人工修改，能说明“改了什么、为什么改”。

与实验一相比，实验二的重心从“问清楚要什么”转到“决定怎么做”。同一个需求可以有很多种设计，报告要回答的是：为什么选这一种，代价是什么。

# 第二章 软件架构与模块划分

## 2.1 项目与需求基线

甲方是一家区域连锁酒店集团，直营 18 家、加盟 28 家，共 46 家门店，覆盖上海、杭州、南京、苏州、成都、武汉 6 个城市。一期没有统一预订系统，存在四类问题：旺季超卖、到店无房；加盟店私自关房、改价；改退单与对账靠电话和手工；跨日库存经常算错。

实验一共形成 51 条需求（功能 39、非功能 8、约束 4）。与设计直接相关的硬约束有：

- 自营渠道零超卖，同店同房型同日按 10 笔并发下单设计（REQ-049）；
- 线上预付锁房 15 分钟，到店现付前台确认 30 分钟（REQ-014/018）；
- 订单 7 个状态，已入住不可取消、已离店不可改单（REQ-016/017）；
- 一单可订多间，但同门店、同房型、同一日期区间；不同房型拆单（REQ-015）；
- 到店无房、停业、支付异常各有处置主体（REQ-027/028/029）。

一期不做会员/积分、电子发票、OTA 对接、房态/房号管理与离线操作。房态被明确拒绝后，房号只在入住时分配、退房释放，系统不维护“待清洁/维修”状态。

## 2.3 模块交互

**下单主链**：M3 先做幂等校验（订单号 + 请求号），再调 M2 按自然日逐日校验库存；M2 用条件更新 `total - sold - locked - group_locked >= qty` 预占，影响行数为 1 才成功；M3 创建待支付订单，线上预付走 M4 支付、回调后把 `locked` 转 `sold`，到店现付由前台 30 分钟内确认；超时由 S3 扫描、M3 取消、M2 释放，S1 异步通知。

**履约链**：M5 办理入住时调 M3 校验状态、调 M2 分配房号；退房时 M5 调 M3 核销、M2 释放库存。M5 不直接写订单表，也不直接改 `sold`。

**改退链**：M3 先校验目标日期/房型可售，再在同一事务内“回退原库存 + 占用新库存”，最后调 M4 计算差价或退款；任一步失败整体回滚。

**异常与报表**：M5 标记订单级异常并提交集团审核，M3 按审核结果执行退款/改期/转店；支付掉单、退款失败由 S3 识别、M4/M6 对账，S1 推送门店与运营，门店只协助核实。M6 只读从库、T+1 汇总，导出走 S2，不参与交易事务。

三条原则：同步只保留下单校验与库存预占；库存是唯一事实源，订单、支付、履约都只能调 M2；跨模块只走接口，不直接改对方表。

## 2.4 关键设计取舍

**库存独立成 M2。** 替代方案是在订单表上 `left = left - 1`。单店低并发能用，但“先查后写”无法满足 10 笔并发与零超卖；加行锁又会把下单串行化。最终选择独立 `DailyInventory`，以 `(hotelId, roomTypeId, bizDate)` 为唯一键，用条件更新原子预占，Redis 只做缓存。代价是多一次服务调用与一张日粒度表，换来可验证的零超卖。

**支付独立成 M4。** 支付网关是外部依赖，回调可能重复、乱序、丢失；退款还有审批与渠道失败。把支付放进 M3 会让订单事务被外部超时拖住，也无法做幂等与对账。M4 独立后，支付单与订单通过业务单号关联，回调只改支付单并通知 M3。代价是多一次跨模块调用与一张支付流水表，收益是资金链路可对账、可重试。

**订单保存房型/价格快照。** REQ-036 要求历史订单锁定下单时的门店、房型、价格。若订单详情实时 join 房型表，后台改一次名称或基准价，历史订单就会“变脸”。方案是下单时把房型名称、成交单价、日期区间写入订单与房明细。代价是数据冗余，收益是历史可追溯。

**异常按处置权拆三类。** 最初把到店无房、支付掉单、退款失败都塞进“待处理异常”，给前台一个“处理”按钮。推演后发现：前台没有权限补录支付订单；集团不审核就不能关闭异常；停业退款不受 24 小时与 500 元限制。于是拆成 06A（前台发起、集团审核）与 06B（店长停业、前台协助核实支付异常），代价是多两屏与“待审核/已裁决”子状态，收益是权限边界与审计链清晰。

**报表只读。** M6 只读从库、T+1 汇总，牺牲实时性换交易稳定性；页面标注数据截止时间，避免把 T+1 数据当实时数据。

# 第三章 UML 建模

## 3.1 图的选型

UML 分结构、行为、交互三类。实验要求类图必画，每类至少一种。本项目的选型如下。

表3-1 UML 图选型

| 类别 | 图 | 回答的问题 |
|---|---|---|
| 结构 | 类图（必画） | 交易域有哪些实体、关系与约束 |
| 结构 | 组件图 | 7 个模块如何组成系统、依赖谁 |
| 结构 | 部署图 | 上线后部署在哪些节点、如何容灾 |
| 行为 | 用例图 | 6 类角色分别能做什么 |
| 行为 | 状态图 | 订单 7 状态如何流转、哪些转换被禁止 |
| 行为 | 活动图 | 一次下单经过哪些判定 |
| 交互 | 时序图 | 抢最后一间房时各部件如何交互 |

没有单独画对象图、包图、通信图与复合结构图：对象图只是类图某一时刻的实例，包图已被组件图的分层覆盖，通信图与时序图语义等价，复合结构图在本项目没有复杂的内嵌结构。取舍原则是：每张图都要回答一个别处回答不了的问题。

绘图统一用 PlantUML 1.2025.10、JDK 21、`dpi 200`、微软雅黑、主色 `#1F3A5F`；`.puml` 与 `.png` 一并交付。

## 3.2 用例图

![用例图](lab2/UML/UML用例图.png){width=16cm}

**目的**：界定 6 类角色的权限边界与一期范围。

**说明**：6 个参与者、16 个顶层用例；店长用 `前台 <|-- 店长` 继承前台的入住、退房、标记异常与查询；No-show 由夜审自动判定，不是人工用例；异常拆成前台“标记异常并提交”与集团“审核异常订单”；会员/积分、OTA、电子发票、房态管理在一期范围外。

## 3.3 类图

![类图](lab2/UML/UML类图.png){width=16.4cm}

**目的**：表达交易域的核心实体、关系与不变量，尤其是“库存为什么不会被扣成负数”“历史订单为什么不会变”。

**说明**：11 个核心类。`DailyInventory` 以 `(hotelId, roomTypeId, bizDate)` 为唯一键，`available = total - sold - locked - groupLocked ≥ 0`，订单锁房与协议锁房分开计量；`Order` 保存门店、房型名称、入住/离店日期、金额与状态；`OrderItem` 只保存间数、已取消间数、成交单价；`Payment`/`Refund` 关联订单，退款 >500 元需店长审批。

**理由**：AI 初稿把 `roomTypeName`、`checkIn`、`checkOut` 放在 `OrderItem` 上，等于允许“一单多房型、每间不同日期”，与 REQ-015/030 冲突。人工把房型与日期上移到 `Order`，`OrderItem` 只保留间数与价格快照，既支持同房型多间与按间部分取消，又保持“一单一房型一日期区间”。

## 3.4 组件图

![组件图](lab2/UML/UML组件图.png){width=16.4cm}

**目的**：说明 7 个业务模块如何组成系统、谁依赖谁、哪些能力是横切或异步的。

**说明**：接入层为小程序、PC、门店后台、集团后台，统一经 API 网关（鉴权、限流、幂等）进入；应用层为 M1–M7；基础设施为 MySQL 主从、Redis、支付网关。关键依赖：M3/M5 → M2 预占/释放；M3 → M4 创建支付单；M4 → M3 回调；M6 → 从库只读；M2 → Redis 热点缓存。S1/S2/S3 放在图例与部署图中。

**理由**：组件图要能回答“改一个模块会不会牵动一片”。本图刻意让 M3 只依赖 M2/M4，M6 只读从库、不反向写交易库；M7 不画成“每个模块都依赖它”的蜘蛛网，而由网关统一鉴权。图例补 S1/S2/S3 的落点，避免读者误以为通知、导出、调度不存在。

## 3.5 状态图

![状态图](lab2/UML/UML状态图.png){width=16.4cm}

**目的**：定义订单 7 个状态、允许的转换、守卫条件与禁止转换。

**说明**：待支付可转已确认待入住或已取消；已确认待入住可转入住、取消、No-show 或异常；已入住可转正常离店或异常；异常订单经集团审核通过后转已取消（退款/转店）或正常离店（在店和解/同店安置）。禁止：已入住 → 已取消；已入住/已离店 → 改单、改金额；已取消/已离店 → 恢复。

**理由**：AI 初稿把异常出边写“处置完成”，没有集团审核守卫，等于前台可以关单；还把“转店安置”记成正常离店，会污染出租率。人工补上“集团审核通过”守卫与“待审核/已裁决”子状态，并注明审核期间保留库存、支付掉单/退款失败只走异常台账。

## 3.6 活动图

![活动图](lab2/UML/UML活动图.png){width=8.6cm}

**目的**：展开一次下单从查询到确认的判定链。

**说明**：顾客提交后先做幂等校验，重复请求返回已有订单；库存按自然日逐日校验，任意一天不足即整单拒绝；线上预付走支付网关，成功则 `sold + qty、locked - qty`，失败/超时释放；到店现付由前台 30 分钟内确认，否则自动取消；失败提示保留已填信息（REQ-051）。协议锁房不经过本流程。

**理由**：活动图没有用泳道，因为 PlantUML 在泳道内嵌套分支时连线容易乱穿。改用“责任方前缀 + 注释”后，谁做什么仍然清楚，图也不会变成线团。

## 3.7 时序图

![时序图](lab2/UML/UML时序图.png){width=13.2cm}

**目的**：讲清“两个人同时抢最后一间房”时，系统靠什么保证只有一单成功。

**说明**：A 先执行 `UPDATE ... SET locked = locked + 1 WHERE total - sold - locked - group_locked >= 1`，影响行数 = 1，锁房成功；B 执行同一条件，影响行数 = 0，返回无房并保留已填信息；A 支付成功后 `sold + 1、locked - 1`；15 分钟未支付由定时任务释放。注释说明数据库条件更新是最终判定，Redis 只做缓存/加速。

**理由**：AI 初稿让 Redis 做“预占成功”的最终判定，缓存故障或主从延迟时会超卖。人工把最终判定放回 MySQL 条件更新，并画出影响行数 1/0，因为这是并发正确性的证据，不是实现细节。

## 3.8 部署图

![部署图](lab2/UML/UML部署图.png){width=16.4cm}

**目的**：把非功能需求落到节点：99.9% 可用性、RPO≈0、报表只读、门店断网降级。

**说明**：用户侧经 Nginx 进入应用集群（≥2 节点）；数据层为 MySQL 主库 + 只读从库、Redis 哨兵、对象存储、备份存储；外部为支付网关与短信；调度任务负责订单超时、锁房到期、夜审。主从同城同步，RPO≈0；门店断网时手工登记、恢复后补录。

**理由**：AI 初稿写 99.99%、RPO=0，并把 MySQL 画成单节点，既超出甲方指标，也无法由架构保证。人工改为 99.9%、RPO≈0，补上应用集群、主从、哨兵、每日全量 + binlog 与断网降级。部署图写下的每个数字都要有对应的冗余手段。

### 4.3.1 界面01 首页选店

# 第五章 AI 辅助设计记录

## 5.1 使用原则

本次实验把 AI 放在“初稿与格式”位置，不放在“拍板”位置。

- 人先定义规格：先写清楚要回答的问题、输入需求编号、输出格式，再让 AI 生成。
- AI 产出必须可核对：每张图、每屏 UI 都要能指回 REQ 与人工修改记录。
- 钱、时限、合规、权限不由 AI 决定：500 元上限、15/30 分钟、99.9%、六角色权限全部以需求为准。

## 5.3 优缺点与“人只做检查校对”

通过本次实验，感受到 AI 根据需求生成 UML 的能力较强，而设计可用 UI 的能力较差。

AI 设计 UI 时，缺乏对现实场景的想象能力。如 01 图初版中，有一个“附近酒店”推荐页，AI 未考虑到游客一般在家预订酒店。

同时，AI 在某种程度上分开生成了 UI 的每一张示意图，而没有把它们作为一个整体设计，从动态的业务流程视角考虑。生成每一张图时，只是在界面上盲目堆砌相关元素，对各界面的用途和关系缺乏考虑，设计出的 UI 初看与现存的应用很相似，但逻辑混乱，存在大量意义不明的元素。如初版的 02 图下方有一个类似购物车的总价标签，但在选房流程中此时不可能知道总价。

我在大半年前用 AI 生成过一个小程序 demo，当时 AI 的这类问题就十分严重。如今，AI 设计界面的审美大幅提高，但设计的逻辑问题和之前区别不大。私认为，UI 的逻辑问题与人类使用软件时的体验相关，这方面缺乏训练资料。AI 使用软件的方式和人类有很大区别，要提高 AI 的界面设计能力，就要让它理解人类使用软件的动态过程。

同时，现有的 UI 设计工具和方法可能不适合 AI：最终产出是一堆图片，这可能鼓励 AI 将界面视为图片的静态集合，在生成图片的过程中和结束后，不会从业务流程视角反思 UI 设计的合理性。

总而言之，想让现在的大模型完成几乎所有设计工作，人只进行检查校对不太可能。从安全角度看，很容易产生业务逻辑漏洞。从用户体验角度看，模型和人类的感受之间有 gap，设计的软件不易于使用。软件前端与用户进行最直接的交互，许多用户体验难以量化，设计时仍需要人的深度参与。
