## 3. 每屏说明

### 01 首页选店
**目标**：先把"住哪家店"定下来，再看这家店有什么房。
**布局**：品牌头部 → 选店卡（城市/具体门店/日期/人数）→ 该店房型速览 → 底部 Tab。
**关键状态**：已选门店明确展示"云栖酒店 · 外滩店"；房型卡显示"仅剩 3 间/5 间/1 间"；选店卡右上角显示"2 晚 · 2 位"。
**交互**：选城市 → 选/更换门店 → 选日期与人数 → 查看房型；间数留到 02A 房型详情再选。
**理由**：客人通常在家规划行程，"附近酒店"没有意义；先定门店再定房型，才符合"城市 → 门店 → 房型"的决策顺序。房型速览只做推荐，详细比较在 02，价格与间数在 02A。

### 02 选房型
**目标**：只解决"住哪种房"，不在列表页定数量与总价。
**布局**：酒店信息 → 日期条（仅日期与晚数）→ 筛选 → 房型列表（图片/描述/余量/标签/起价/进入箭头）→ 底部提示。
**关键状态**：仅剩 3/5/1 间、可取消、含双早。
**交互**：筛选 → 点整张房型卡 → 02A 详情。
**理由**：列表页同时出现"间数 + 总价"会把选房型和定数量混成一步，价格也容易被误读成最终价；02 只承担比较，间数与金额留给 02A。

### 02A 房型详情
**目标**：在选定房型后确定间数，并让顾客核对"钱花在哪"。
**布局**：头图 → 房型名/床型/含早 → 每晚价与余量 → 入住日期 → 间数步进器 → 价格明细（单价 × 晚数 × 间数）→ 预订须知 → 底部合计与"确认下单"。
**关键状态**：间数 2、仅剩 3 间（步进器上限=余量）、合计 ¥2272；一单只允许一个房型，需要其他房型时提示分开下单。
**交互**：加减间数 → 确认下单 → 锁房（15 分钟）→ 03 填单。
**理由**：先选房型再定数量，符合顾客决策顺序；把 568 × 2 晚 × 2 间 拆开写，顾客能自己核对；确认下单才触发锁房，避免在列表页反复进出就占用库存。

### 03 填单锁房
**目标**：在锁房倒计时内完成入住人填写并进入支付。
**布局**：倒计时头部 → 锁定提示条 → 入住人表单 → 订单信息与价格明细（2 间 × 2 晚 = ¥2272）→ 预订须知 → 底部支付栏。
**关键状态**：14:32 倒计时持续可见；字段校验失败时保留已填内容（REQ-051）；2 间房需 2 位入住人，未填满时提示"还需 1 位"。
**交互**：填写 → 去支付；超时自动释放。
**理由**：倒计时放在头部而不是角落，降低"填到一半房没了"的焦虑；把 02A 选定的间数与金额原样带入，顾客不用二次核算。

### 04 支付
**目标**：一次完成支付，减少误付。
**布局**：待支付金额 → 支付方式（微信/支付宝/银行卡）→ 支付安全 → 订单摘要 → 底部实付。
**关键状态**：默认选中微信；金额与订单摘要同屏核对。
**交互**：切换方式 → 确认支付 → 支付结果。
**理由**：支付页最怕"付错金额/付错单"，所以把订单摘要放在按钮上方。

### 05 订单改退
**目标**：让顾客自助完成改期/取消，减少客服。
**布局**：状态卡 → 房型与入住人 → 订单进度时间轴 → 取消规则 → 修改/取消 → 联系酒店/客服。
**关键状态**：已确认待入住；24 小时内外不同违约金（示例 2 间首晚 ¥1136）。
**交互**：修改订单 → 改期/改房型；取消订单 → 退款预览。
**理由**：规则放在按钮之前，避免"点了取消才知道扣钱"。

### 06 今日工作台
**目标**：前台一屏看清今天要接待谁、谁要退房、哪里出问题，并把异常按"谁能处理"分流。
**布局**：4 个 KPI → 今日到店表 → 待处理异常（需门店处置 / 协助核实）→ 快捷操作。
**关键状态**：待处理异常 2 = 需门店处置 1（到店无房）+ 协助核实 1（支付异常）；房号显示"待分配"，与 REQ-025 一致。
**交互**：办理入住 → 右侧抽屉；"处理 >" → 06A；"核实 >" → 06B。
**理由**：前台是高频扫视场景，表格密度高于卡片；异常不按类型堆叠而按处置权分组，避免前台点开支付异常却无事可做。

### 06A 异常处置
**目标**：把"到店无房 / 在店纠纷"从发现到提交审核一次做完，并留下赔付与安置记录。
**布局**：左侧待处置工单 + 最近处置记录 → 右侧处置面板（订单快照、异常原因、同城安置、赔付/安置费、通知记录）→ 暂存 / 提交集团审核。
**关键状态**：周敏到店无房已等待 25 分钟；订单仍为已确认待入住；提交后转"异常订单（待审核）"，库存保留。
**交互**：选工单 → 填安置门店/房型/日期/间数与费用 → 提交集团审核；已提交工单只读。
**理由**：前台只有发起权，终审在集团，所以按钮写"提交集团审核"而不是"完成处置"；费用与通知同屏，避免事后补录对不上账。

### 06B 停业与支付异常
**目标**：停业时批量处理受影响订单；支付异常只做协助核实，不越权补录或退款。
**布局**：左侧停业中的受影响订单表（通知状态、批量通知/全额退款）；右侧支付异常订单 + 门店核实字段 + 提交运营。
**关键状态**：临时停业中 12 单（已通知 8 / 待通知 4）；退款失败"财务处理中"；门店核实"客人已离店 / 凭证已核对"。
**交互**：店长发起/恢复临时停业 → 处理受影响订单；前台核实支付异常 → 提交运营核实。
**理由**：停业退款不受 24 小时与 ¥500 上限限制，必须与普通取消分开；支付掉单/退款失败归财务、运营，门店越权补录会破坏对账与台账。本屏按店长视角绘制；前台登录时只保留右侧"支付异常协助核实"，不显示停业与批量退款。

### 07 库存与房价
**目标**：店长按日维护价格与库存，并处理关房/协议锁房。
**布局**：房型与月份工具栏 → 4 个概览 → 7 日×5 房型日历 → 图例。
**关键状态**：可售（绿）、≤2 间（橙）、满房（红）、协议锁定（紫）。
**交互**：点单元格 → 调价/关房/锁房；批量调价。
**理由**：日历热力图能一眼看出周末与展会的供需；协议锁房必须与普通库存同屏可见。

### 08 订单检索与入住
**目标**：前台用订单号/手机号/姓名快速定位、办理入住，或从异常订单直接进入处置。
**布局**：搜索栏 → 状态 Tab（今日到店/待入住/已入住/异常/全部）→ 订单表 → 右侧入住抽屉（证件、分房、押金、备注、确认）。
**关键状态**：待入住/已确认/异常/已入住；异常行带"处置 >"；示例订单 0018 为 2 间、¥2272，与客人端 03–05 一致。
**交互**：检索 → 选中订单 → 核验 → 分房 → 确认入住并制卡；异常 Tab → 处置 → 06A。
**理由**：异常单独成 Tab，才能从"今日到店"里把异常单捞出来；抽屉保留列表上下文，前台不用在页面间跳转。

### 09 门店与房型
**目标**：集团统一维护门店与房型，门店只读。
**布局**：门店表 → 右侧详情（档案、房型参数）→ 权限提示。
**关键状态**：营业/筹备/停业；直营/加盟。
**交互**：新增门店、编辑档案、查看房型参数。
**理由**：把"门店无房型编辑权限"直接写在详情里，权限边界可见，减少误操作。

### 10 经营报表
**目标**：集团与城市经理看经营结果并对账。
**布局**：城市/月份/类型筛选 → 4 个 KPI → 出租率趋势 → 城市排行 → 门店明细。
**关键状态**：T+1 更新；直营+加盟可分开。
**交互**：筛选 → 下钻门店 → 导出 Excel。
**理由**：从宏观 KPI 到城市排行再到门店明细，符合"先看异常、再定位"的分析路径。

### 11 权限与审计
**目标**：配置六类角色权限，并追溯关键操作。
**布局**：角色权限矩阵 → 角色说明（城市经理只读）→ 最近操作日志。
**关键状态**：✓ 允许 / — 拒绝；城市经理仅"查看报表"。
**交互**：勾选权限、查看日志、按角色筛选。
**理由**：矩阵比逐个角色点开更直观；城市经理列单独说明"只读 + 按城市过滤"。
