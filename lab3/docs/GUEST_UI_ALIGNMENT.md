# 客人端 UI 与实现对照说明

- 对照对象：实验二 UI 稿 `lab2/UI界面/界面01~05`（含 `02A`）与实验三实现 `lab3/hotel_booking/ui/`
- 结论：实现已按设计稿重做，6 屏的版式、字号、配色、组件与交互顺序与设计稿一致；数字与门店名来自真实服务层数据，因此与设计稿示例值不同
- 验证：`report/screenshots/02-guest-home.png` ~ `07-guest-order.png` 为 1:1 实机截图（390×844）

## 1. 改造前的差异

| 屏 | 设计稿 | 改造前实现 | 差异性质 |
|---|---|---|---|
| 01 首页选店 | 品牌头图 + 选店卡（城市/门店/日期）+ 该店房型速览 + 三 Tab | 一张筛选表单（城市下拉、ISO 日期输入框、人数、最高价、含早勾选）+ 跨店结果列表 | 信息架构不同：设计稿是“城市→门店→房型”，实现是“全平台条件筛选” |
| 02 选房型 | 门店头图 + 日期条 + 筛选项 + 房型卡（图/规格/余量/起价/箭头） | 没有独立页面，与跨店结果混在 01 | 缺少页面与“只比较房型、不出现总价”的规则 |
| 02A 房型详情 | 头图 + 单价/余量 + 间数步进器 + 价格明细 + 预订须知 + 合计确认 | 有详情页，但显示总价、无间数选择、无价格明细，按钮为“立即预订” | 缺少“先定间数再下单”的关键交互 |
| 03 填单锁房 | 倒计时头 + 锁定提示条 + 入住人表单 + 订单信息 + 去支付 | 表单里塞了间数、支付方式、“立即模拟支付”勾选；无锁房倒计时 | 页面职责错位，锁房机制不可见 |
| 04 支付 | 独立收银台：待付金额、三种支付方式、支付安全、订单摘要、确认支付 | 没有支付页，提交订单时顺带支付 | 缺少关键确认环节 |
| 05 订单改退 | 状态卡 + 房型卡 + 进度时间轴 + 取消规则 + 修改/取消/联系 | 订单详情只有字段罗列和支付流水 | 缺少时间轴、取消规则与自助改退入口 |
| 全局 | 深蓝渐变头部、白卡 12–16 圆角、胶囊标签、9–30px 字号、底部三 Tab | ttk 原生控件（灰底输入框、系统下拉、方角卡片）、小字号、底部两 Tab | 设计系统未落地 |

## 3. 逐项对齐清单

1. **版式**：每屏严格按 390×844 栅格绘制，元素坐标取自设计稿源码（如 01 卡片 20/180/350×224、03 表单卡 16/170/358×232）。
2. **字体**：微软雅黑；正文 10–13px、辅助 9px、标题 17–27px，按 96dpi 换算为 Tk 点值，画布与文字比例固定。
3. **配色**：主色/辅助色/成功/警告/危险/分隔线全部取自设计 token；订单状态色统一由 `STATUS_COLORS` 提供。
4. **组件**：白卡圆角 12–16、按钮圆角 10、胶囊半径 999、阴影用双层浅灰模拟；房型图用设计稿同款渐变占位（圆 + 两条白条）。
5. **导航**：01/订单/我的三 Tab（首页/订单/我的），二级页统一左上角返回箭头；02、03、04 的头部带渐变与状态栏。
6. **信息层级**：02 列表不出现总价，只出现“起/晚”；02A 才出现间数与“单价 × 晚数 × 间数”的明细；03/04 的金额与订单摘要始终同屏。
7. **状态**：余量紧张用琥珀胶囊、满房用红色、锁房超时转红条并禁用“去支付”、取消规则随当前时间切换文案。
8. **输入**：表单输入框嵌入卡片行内（无边框、仅下划线），底部弹层承担城市/门店/日期/人数/到店时间/取消原因等选择。
9. **轻量操作**：联系酒店、在线客服、关于云栖使用底部小面板（标题 + 号码/版本 + 复制号码），只覆盖底部一小段，原页面保持可见。

## 4. 为对齐设计稿补充的数据字段

设计稿出现了“★★★★★ 4.8 / 5”“28㎡”“到店时间”“添加入住人（还需 1 位）”，原模型没有对应字段。为了不写死假数据，按真实模型补充：

| 字段 | 位置 | 说明 |
|---|---|---|
| `Hotel.star` / `Hotel.rating` | `domain/models.py`、`hotels` 表 | 02 门店头部的星级与评分 |
| `RoomType.area_sqm` | `domain/models.py`、`room_types` 表 | 房型卡的“28㎡”与详情页 ㎡ 胶囊 |
| `Order.arrival_time` | `domain/models.py`、`orders` 表 | 03/05 的“到店时间” |
| `order_guests` 表 | `infrastructure/schema.py`、`OrderRepository` | 多间房的多位入住人（REQ-015 的 2 间 2 位） |

已有数据库通过 `Database._migrate_columns()` 自动补列并回填主数据，无需删库重建。

## 5. 与设计稿的有意差异

1. **数字不同**：设计稿示例是 ¥568 × 2 晚 × 2 间 = ¥2272；实现显示真实报价（受城市系数、房型系数、周末价影响），版式与计算方式一致。
2. **状态栏时间**：设计稿固定 9:41，实现显示真实系统时间，其余信号/WiFi/电池图形一致。
3. **订单列表与“我的”**：设计稿只覆盖主路径 6 屏，这两个 Tab 按同一设计语言补画，避免点 Tab 无响应。
4. **不可订状态**：设计稿未画满房/停业/关房，实现沿用同一套胶囊与文案展示真实原因。
5. **多间房上限**：设计稿写“最多 3 间”，实现显示真实余量，同时受服务层 1–9 间的约束。
6. **失败反馈**：设计稿未画错误态，实现用同色系浮层提示（如手机号格式、锁房释放、超时取消），不改变页面结构。
7. **遮罩方式**：Tk 画布没有 alpha 通道，整页深色遮罩只能画成可见网点，所以弹层不做整页变暗，改为只从底部升起面板，原页面保持可见；关闭用 ✕ 或“取消”。
