# 大模型辅助开发记录（摘录）

> 用途：为实验报告第 3 章提供可追溯的过程材料。这里记录的是实际使用过的提示词方向、模型输出中被采纳/被否决的部分，以及人工复核后做的修改，不是“让模型一次性生成整个项目”的聊天记录。

- 工具：DeepSeek Harness（DeepSeek-V4-Flash）
- 使用时间：2026-11-25
- 原则：模型负责“给出候选实现/测试/文案”，人负责“读每一行、跑测试、改错、决定取舍”

## 1. 工作流

```
需求条目（REQ-xxx）
   ↓ 提取实体、状态、约束
UML 类图 / 状态机
   ↓ 让模型先写“存根 + 规约”，不直接写完整实现
接口与测试清单
   ↓ 人确认签名和验收条件
小步生成实现
   ↓ 每步运行测试 / 编译 / 风格检查
人工审查 diff
   ↓ 发现错误后把错误现象和期望行为反馈给模型
修正并补充回归测试
```

## 2. 代表性提示词

### P-01 从需求抽取领域模型

```text
你是酒店预订系统的 Python 架构师。下面是需求文档中与交易域相关的
REQ-008/009/014/015/016/017/018/019/020/021/022/023/024 片段。
请只做三件事：
1) 列出实体及其唯一键；
2) 列出不能违反的不变式（用“必须/禁止”表述）；
3) 指出需求中互相冲突或需要人工决定的地方。
不要写代码，不要补充需求里没有的业务。
```

模型输出被采纳的部分：`DailyInventory` 的唯一键、`available` 不变式、`Order` 一单一房型。
被人工修正的部分：模型最初把“首晚房价”等同于订单均价，人工改为在 `OrderItem` 增加 `first_night_price` 快照。

### P-02 先存根后实现

```text
根据下面的类职责，生成 Python 3.12 的类与方法存根，要求：
- 只使用标准库，金额用 Decimal；
- 每个方法写一句 docstring，说明前置条件、副作用、抛出的领域异常；
- 不要填方法体，不要引入 ORM；
- 所有公开方法必须有类型标注。
```

这样做的目的：先审查接口与职责，避免模型直接生成大量“看起来能跑、实际口径错误”的代码。
实际项目中 `BookingService` 的 `create_order / pay_order / cancel_order / modify_order`
四个入口就是先定签名，再逐个补实现和测试。

### P-03 让模型设计并发测试

```text
为“两个客人同时抢最后一间房”写一个 unittest：
- 把某房型某天 total 改为 1；
- 两个线程用 Barrier 同时调用 BookingService.create_order；
- 断言恰好 1 个成功、1 个抛 DomainError；
- 断言最终 locked=1、available=0；
- 不依赖 pytest，使用标准库 threading 和 unittest。
```

模型给出线程 + Barrier 的骨架。人工补了：每个线程独立的手机号、异常捕获范围、
SQLite `busy_timeout`、测试数据库放在 `lab3/data`（工作区临时目录在该环境下不可写）。

### P-04 代码审查

```text
请以“挑错”为目标审查下面这段 cancel_order：
- 是否有事务提交后又用新连接读旧数据的问题；
- 退款金额是否可能超过已支付金额；
- 部分取消时 total_amount 是否与剩余间数一致；
- 是否有异常路径导致库存已释放但订单未取消。
只输出问题、证据行号和最小修复建议，不要重写整个文件。
```

模型确实找出了“事务内新连接读取未提交数据”的问题，并建议返回已变更的聚合对象。
人工进一步发现：`pay_order` 在超时分支里先写取消再 `raise`，会被事务上下文回滚，
于是把超时处理改成“先完成事务，再在事务外抛业务异常”。

### P-05 GUI 结构与可测试性

```text
用 Tkinter 设计三端桌面客户端：客人端、门店端、集团端。
约束：
- 不引入第三方 UI 库；
- 颜色统一为深蓝 #12263A / 金色 #C9A227 / 浅灰 #F4F6F9；
- 页面只调用 Services，不直接写 SQL；
- 至少给出登录、搜索、工作台、库存、退款审核、报表 6 个页面；
- 表格用 ttk.Treeview 封装，便于后续替换。
```

模型给出了页面骨架。人工修正了 `pack` 与 `grid` 混用导致的 TclError、
弹窗底部重复“取消”按钮、工作台两列表格宽度不足等问题。

## 3. 模型输出与人工处置对照

| 模型输出 | 是否采纳 | 人工处置 |
|---|---|---|
| 用 SQLite 单文件保存演示数据 | 采纳 | 增加 WAL、外键、条件 UPDATE、事务封装 |
| `Order` 上用 `status: str` | 否决 | 改为 `OrderStatus` 枚举 + 白名单转换表 |
| 金额用 `float` | 否决 | 改为 `Decimal`，SQLite 以两位小数 TEXT 存储 |
| 退款金额 = 实付 - 首晚均价 | 否决 | 改为订单首晚成交价快照，并区分部分取消 |
| 取消时先 `raise` 再释放库存 | 否决 | 先完成释放/取消/审计事务，事务外再抛业务异常 |
| 线程测试直接共享一个 connection | 否决 | 每个操作独立 connection，事务内 `BEGIN IMMEDIATE` |
| 在事务内用新连接查订单状态 | 否决 | 使用已变更的聚合对象，事务提交后再重读 |
| Tkinter 页面直接拼 SQL | 否决 | 页面只依赖 Services / Repository 的只读查询 |
| 自动生成 29 个测试 | 部分采纳 | 删除重复测试，补上特殊日期、部分取消、误操作拦截等边界 |

## 4. 人工审查发现的具体缺陷

### D-01 超时支付取消被回滚

- 现象：`pay_order` 在超时分支里释放库存、更新订单，然后 `raise ConflictError`；
  异常被 `with db.transaction()` 捕获后回滚，订单仍然是待支付。
- 修复：在事务内设置 `expired = True`，完成取消与审计并提交；事务外再抛异常。
- 回归：`test_expired_payment_cancels_atomically`。

### D-02 取消后返回旧状态

- 现象：`cancel_order` 在事务内用新连接 `self.orders.get()` 重新查订单，
  SQLite 尚未提交，读到旧状态，前端显示“待支付”。
- 修复：返回已变更的 `order` 聚合对象，事务提交后再由上层刷新。
- 回归：`test_multi_night_lock_and_release`、`test_partial_cancel_keeps_remaining_room`。

### D-03 首晚房价口径错误

- 现象：`OrderItem.unit_price` 被当作首晚价，实际它是整段住宿的单间总价；
  500 元退款审批线在高价房型上判定错误。
- 修复：增加 `first_night_price` 字段，创建订单时写入 `Quote.first_night_price`，
  退款审批只使用该字段。
- 回归：`test_refund_over_500_needs_approval`、`test_refund_under_500_auto_approves`。

### D-04 模型插入 docstring 破坏多行签名

- 现象：批量补文档时，脚本把 docstring 插到 `def foo(` 与参数列表之间，导致语法错误。
- 修复：改为在右括号与返回类型之后插入；用 `compileall` 每次验证。
- 说明：这是“自动化改动也要逐步验证”的反例，模型/脚本都不能替代编译检查。

### D-05 报表金额浮点误差

- 现象：模型在 SQL 中用 `SUM(CAST(amount AS REAL))` 统计营收。
- 修复：查询明细后在 Python 中用 `Decimal` 聚合。
- 回归：`test_report_totals_are_consistent`。

### D-06 环境限制

- 现象：当前运行环境的沙箱不允许在新建临时目录里创建 SQLite 文件，
  也不允许 pip 安装 pylint。
- 处理：测试数据库改到 `lab3/data`；代码风格检查改为项目内
  `tools/check_style.py`（100 列、行尾空白、制表符、模块/类文档、裸 except），
  并在 `pyproject.toml` 中保留 Pylint 配置供有网络的机器复现。
